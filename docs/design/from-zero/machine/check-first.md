# Check first: proof has a boundary

## 1. The idea

Before committed work starts, write what would count as done, how each line will be checked, and who has authority to accept it. Replaceable doers offer versions; separate checkers try to disprove both those versions and the interpretation of the request, with a durable record and clocks doing the coordination. Passing the independent checks earns a showing, not proof that we understood him: unfamiliar taste and intent still need his reaction, while narrow, reversible work may finish under authority he has already granted.

## 2. What is kept in the record

One authoritative record accepts each change atomically, preserving its previous version; files and proof live beside it under fingerprints that identify their exact contents. All entries carry author, time, goal, agreement version and the event that caused them; corrections append rather than erase history. The following names are internal; he sees plain words.

| Thing | Fields beyond those common fields | Who may write it |
|---|---|---|
| Goal and agreement | Original sentence; source; intended benefit; examples and counterexamples; done lines; exclusions; assumptions; permitted actions; costs and undo limits; dependencies; promise; par; acceptor | A counterpart run proposes; he accepts, amends, stops or delegates within existing authority |
| Done line and check | Plain words; source in his request or ruling; example that should fail; checker type; recipe; inputs; proof needed; current result: untested, fail, pass or unknown | A check designer proposes; a separate challenger admits it before work; changing meaning needs a new agreement |
| Work attempt | Requested outcome; allowed resources; input versions; doer identity; computer; permission expiry; checkpoint and finish times; budget; result location | Dispatcher grants permission; doer appends checkpoints/results; watch expires permission |
| Result and proof | Exact candidate; input fingerprints; executed check versions; raw observations; independent verdict and dissent; changed assumptions; acceptance and follow-up date | Doer submits candidate; scripts and non-makers append proof; authorised acceptor accepts |
| Decision or wait | Issue; relevant evidence; recommendation; authority; default and undo; deadline; consequence; estimated reading minutes; return event; state; delivery receipt | Counterpart prepares; gate changes routing; he answers; watch applies an already-authorised expiry action |
| Ruling and rule | Exact answer; here/always scope; reason; exceptions; authority versus preference; source; effective/expiry dates; replacement; applications and reversals | His answer is immutable; counterpart proposes its interpretation; gate can apply only admitted rules |
| Resource and observation | Computer/capabilities; reserved object; current writer; permission number; last successful observation; next due; observed/reported/checked state | Host scripts report; record service assigns exclusive publication rights; separate watch observes |
| Trust and meter events | Work kind and risk; check/rubric version; first-pass outcomes; later misses; audit selection; costs; attention events; cycle causes | Scripts derive counts from events; he alone grants wider authority |

Never store passwords, sign-in tokens, unnecessary personal data, hidden reasoning, or an assertion of health based merely on no complaint. Keep the original instruction and necessary source evidence with restricted access; redact proof for display, retain its provenance, and record a retention deadline. A helper receives only the slice it may read.

Illustrative Invoice export record: the week supplies six passing lines, not their text, so these six are invented for this example. Lines: file opens on phone and desk; every paid invoice appears once; amounts reconcile; private notes stay out; another customer's invoices cannot be read; retrying produces the same export.

| Moment | Actual record contents, abbreviated |
|---|---|
| Agreement yesterday | Invoice export; agreement 1 accepted; intended benefit: usable accounting handoff; six lines above frozen with check recipes; he accepts result; file cadence and date zone delegated within export-only scope; no sending to accountant; show Tuesday; cycle 1/par 2; six untested |
| Tuesday, before sitting | Candidate 3 and inputs fingerprinted; checks 1–6 pass, scripts reproduced and checker inspected the actual file; assumptions: one file/month, his time zone; no dissent; show exact candidate 3; six of six checked, acceptance pending; cycle still 1 |
| Tuesday, after acceptance | His acceptance points to candidate 3 and agreement 1; cycle 2/par 2; done; ruling retains those two assumptions for this export; follow-up reconciliation due in two days; trust outcome provisional until that check |

The count is never a percentage of effort. Show “six of six checked; needs your look,” or “four pass, one fails, one unknown”; changing a line starts a new denominator and invalidates affected proof without hiding the previous one.

## 3. The runs

Every judgement run starts cold from a bounded packet: current agreement, relevant rulings, named evidence, exact input versions and one requested output. Its receipt lists what it read; missing material is requested explicitly, not replaced with guessed history. No full conversation, periodic wake-up or helper-to-helper status exchange is required.

The agreement's first face targets 120–140 words: what I heard; three to six done lines; what I may decide; what only you decide; exclusions; next showing and par. Detailed recipes stay behind those lines, without hiding a new commitment. If unfamiliar intent will not fit an honest minute, say so and offer a checked sketch; never remove the difficult condition to meet the reading target.

| Job | Starts; reads → writes | Executor; life and rough cost |
|---|---|---|
| Capture and locate | Sentence/voice; source plus project clues → durable intake, likely goal, acknowledgement | Script for capture; helper only if ambiguous; seconds, at most one small judgement run |
| Draft agreement/checks | Intake; nearby examples, rules and authority → short agreement and separate detailed check plan | Counterpart helper; 1–3 minutes, about 2,000 input words plus output |
| Challenge interpretation | Draft; original request and relevant examples → missing intent, false-positive tests, admitted contract or repair | Different helper; 1–3 minutes, similar reading; no maker yet |
| Gate and dispatch | Accepted agreement, fork, answer or timer; current rules/capacity/dependencies → rule receipt, reservation, attempt or parked state | Script; under a second excluding record access; never invents intent or authority |
| Make or repair | Reserved attempt; failing lines and permitted inputs → isolated candidate, checkpoints, concrete fork if necessary | Any capable doer; usually 10–40 minutes; bounded work budget, no judgement about its own acceptance |
| Reproduce and challenge result | Candidate; frozen checks, original request and source data → independently run proof, missing-coverage finding, verdict | Scripts plus different helper; seconds to several minutes, roughly one focused source reading |
| Prepare showing/decision | Proven candidate or unresolved fork → short packet, actual thing and evidence links | Short counterpart run; 1–2 minutes; no rewriting of whole project histories |
| Apply answer/reopen | His answer or a later miss → ruling, amended contract/rule candidate, invalidated proof and necessary repair | Script records; helper interprets ambiguous scope once; 1–3 minutes if needed |
| Watch/reconcile/deliver | Due clocks or undelivered record events → retries, fences, fresh observations, promise change, delivery receipt | Scripts only; seconds per sweep, no judgement helper on healthy ticks |
| Ledger/audit | Weekly timer or selected audit → counted ledger, reproduced sample, proposed trust change | Script counts; helper writes terse explanations; one shared 2–5 minute run/week plus sampled checks |

Judgement belongs in interpretation, making, adversarial review and genuinely new forks. Identity, authority boundaries, duplicate suppression, clock arithmetic, reservations, counts and routing must never depend on a helper deciding to remember them.

## 4. The gate

The gate is the sole ordinary route to him; he and a dissenting checker can open the original record directly. Evaluate each pending item in this order, including again when opened or answered:

1. Honour stop/revoke first; verify current agreement, evidence freshness and dependency state. Merge duplicates, withdraw irrelevant items and refresh stale packets; missing observation reads “unknown,” never ready or healthy.
2. Find an applicable rule. Explicit authority plus matching conditions settles the action and records why; a preference alone can choose a recommendation, never authorise an action. Conflicting or ambiguous authority cannot settle it.
3. Try a timed default only inside existing authority, with bounded reversible effect, tested undo, cost limit and named time. Until then independent work continues; at the time it proceeds without requiring an answer, and the choice remains inspectable. Otherwise the expiry action is to park safely, not assume consent.
4. Reserve attention: start with at most 12 expected minutes ready for the next sitting, no ordinary item older than two working days. Count agreements, showings and decisions together; reserve expected minutes before starting work that will need them, using recent completion/reading rates, not helper count. Excess prepared work stays held; stop admitting more goals and park dependent branches instead of filling a hidden question pile.
5. Apply expiry before presentation: revalidate context at every return event and at least daily. Dead issue → withdraw; stale evidence → recheck; unanswered owner-only choice at its deadline → park with a next review date. Age does not grant authority or justify repeatedly asking the same question.
6. Test the narrow urgent lane: only he can act, waiting until his next sitting has a concrete deadline consequence, and no safe authorised substitute exists. Require current proof of that consequence, a prepared action taking at most two minutes, and one independent urgency check; otherwise hold or park.
7. Put the rest in the next sitting, ordered by cost of delay, then age. A sitting shows its estimated minutes and ends at its reservation; he can choose to open more. Every question states “If unanswered, [specific action or safe stop] at [time]”; “Not now” records a date or dependency and removes the active item.

Urgent delivery uses the same doorway, one push per unresolved consequence, with a receipt. No acknowledgement by the deadline means execute the stated safe stop, not repeat the alarm; only confirmed delivery failure may try the agreed backup channel. Urgent reservations start at two minutes/day; exceeding that permits one combined incident alert with its full consequence, freezes affected new starts and requires a ruling to widen the lane, rather than silently suppressing a real emergency.

At two days old, a still-valid owner-only item becomes one parked goal with a return plan, not a freshly numbered question. If no sitting occurs, dates still advance and the glance reports both backlog age and parked work truthfully. Proposed time/age limits are starting settings to calibrate, not measured human capacities.

## 5. The checks

For each done line, the designer writes an observable example, a contrary example, the conditions of observation and the authorised judge. “Texts arrive early enough” cannot honestly become “the job ran”: check receipt on representative phones at the agreed lead time, local-time transitions, retries without duplicates and the consequence of delivery failure. The actual lead time remains a proposed assumption until supported by a ruling or accepted agreement.

| Kind | What passes; what does not |
|---|---|
| Repeatable fact | A script observes the required behaviour with known inputs and expected outputs; it first fails on the old/broken version and then passes on the candidate. An isolated assertion supplied by the maker is no proof. |
| Judgement with a bounded rubric | Another helper examines the actual result against accepted examples and counterexamples, independently deriving its verdict. “Short, welcoming email” includes a length bound and accepted tone examples; matching them supports a judgement, not certainty about his taste. |
| Only he can judge | A sketch, feel, new tradeoff or “is that what I meant?” is shown to him after every preparatory check passes. The line remains awaiting him; neither silence nor another helper turns it green. |

Each proof identifies the candidate, agreement/check versions, environment, inputs, time, raw outcome and checker. Changing the candidate invalidates affected proof; an integration change reruns shared-boundary checks. A showing opens the actual frozen candidate with a plain line-by-line proof drawer, assumptions and any disagreement; accepting it cannot accidentally accept a later version.

Before making, the challenger asks “Could a useless result pass all of these?” and adds a failing example or marks the gap for his reaction. Before showing, the checker sees the original sentence, contract and result before seeing the maker's claims; chooses its own edge case; and reruns checks from trusted inputs. Makers cannot edit admitted checks, their expected answers or raw proof; proposed changes go back through challenge and invalidate old results.

Judge checkers by outcomes and audit accuracy, never fast approvals, raw defect counts or low cycle counts; record evidenced misses and unsupported objections separately. Seed a known fault when a check is introduced or changed; sample accepted outcomes later. A checker can file dissent directly into the gate-visible record, bypassing preparation; a failed check blocks showing except a checked, clearly labelled diagnostic sketch whose purpose is to settle the missing intent.

Different sessions do not guarantee different blind spots. Use different evidence and, on consequential work, a different method/provider or deterministic comparison; if adequate checking is unavailable, park rather than downgrade the requirement. No checker can disprove every omitted desire: this design explicitly leaves the binary centre at the boundary of intent, and permits a cheap sketch before freezing an expensive contract.

## 6. The watch

Clocks use the record service's time; hosts use elapsed time for local expiry. A watch sweeps each minute; a second, separately hosted observer watches the watch and the record every minute. Only that observer may say the observation system is healthy; neither needs an awake judgement helper.

| Clock | Trips when | Script action |
|---|---|---|
| Work permission | Ten minutes after grant unless host script renews every two minutes | Revoke publication right within the next minute; inspect outputs; reassign an isolated attempt if safe |
| Meaningful progress | Twenty minutes without an artifact/checkpoint advance, even with healthy process signals | Request bounded diagnostic; fence and reroute once; second failure parks branch and revises forecast |
| Dependency | Named event absent at its agreed time; every external wait also has a daily recheck | Query source; try authorised alternative; otherwise park, retaining owner and next date |
| Result/message receipt | Submitted output or important delivery lacks acknowledgement for one minute | Read the authoritative state; retry the same operation number, never start fresh blindly |
| Promise | Remaining measured work no longer fits promised showing time; reevaluated on every state change and every five minutes | Reroute first; if promise moves, record one plain consequence line for glance/next sitting; urgent test only if needed |
| Decision/return | Default deadline, parked date, dependency completion or daily question expiry | Re-enter gate with fresh facts; do not wake a helper merely to notice the time |
| Proof and rule | Relevant inputs change, explicit expiry, or follow-up due; daily scan catches overdue dates | Mark unknown/inapplicable; queue focused recheck, not blanket rereading |
| Observation health | Three minutes without a successful watch/record observation | Independent observer marks doorway unknown with last confirmed time; attempts safe restart or incident delivery |
| Budget and review capacity | Attempt reaches its recorded cost/time ceiling, or expected owner minutes exceed reserved capacity | Stop issuing work; preserve candidate; park or request an authorised budget change |
| Ledger/audit | Weekly close; random sample chosen before outcome; two-day follow-up for newly accepted work | Reproduce evidence, update outcomes and write ledger |

Every retry has a maximum: two automated attempts with the same operation number, then a recorded incident and safe park. Longer tasks must declare intermediate checkpoints, not renew the same unchanging promise indefinitely. An external reply wait never holds a live helper open.

## 7. Rules and trust

An answer first becomes an immutable ruling on that exact candidate and context. Its narrow case-specific rule can apply immediately; the counterpart proposes scope, reason, exceptions, expiry and examples for a broader rule, and asks “here only, or always?” once if his correction did not say. No answer leaves only the case rule; inferred preference remains a recommendation, distinct from permission.

At agreement, dispatch, fork and acceptance, retrieve rules by action, project, work kind, risk and matching conditions; these required fields supply a deterministic shortlist. A helper may find semantic neighbours but must cite the matching conditions, source ruling and current version. Every use records its rule version and affected goals, making revocation and impact review possible.

Current explicit instructions outrank prior standing authority; scoped exceptions outrank their named general rule; expired rules cannot act. Two remaining explicit conflicts cause safe park and one prepared owner decision, never an arbitrary “latest wins.” A failed outcome, changed environment or contradictory answer suspends the rule immediately, traces affected outputs and queues recheck; broad rules require periodic renewal at their stored date.

Trust is kept for a work kind + consequence class + check/rubric version + materially relevant environment, not a helper's reputation. Count independent first-pass checks, first-time owner acceptances, elapsed follow-ups, sampled outcomes, and escaped defects separately; defaults taken and silence are not acceptances. A material change resets the relevant history; one escaped defect suspends autonomy and opens a repair/impact check.

Three consecutive first-time acceptances whose two-day follow-ups passed make a proposal eligible; they do not switch policy. He may authorise low-consequence reversible wording changes to be completed and reported, with a randomly chosen one-in-three shown before use and every result still independently checked. After ten mature successes he may authorise one-in-ten; every widening is explicit, and a miss returns that kind to full showing. These thresholds are conservative trial settings, not statistical guarantees.

Unfamiliar taste, irreversible actions, new private-data access and consequential commitments never earn automatic authority from a success count. Trust changes owner sampling, agreement reuse and par, not checking, security limits or his right to stop. Delegated acceptance is labelled as such, never presented as proof that he personally liked a result.

Full oversight starts at par two, plus a sketch if needed; an explicitly authorised agreement template can reduce it to one showing. Delegated completion makes an unsampled goal par zero; a sample reserves its showing cycle before work starts. Trust never silently edits a running goal's par.

## 8. The meter

Every event is charged to a goal, including retries, discarded work, rule maintenance, preparation and recovery; shared watch/ledger expense is shown separately and allocated by active goal-days with the allocation rule visible. Store provider-reported input/output/cached tokens, actual or unknown money cost, execution seconds, bytes read and packet fingerprint; repeated packet reads measure rereading directly without equating transcript size with context.

A cycle is a return to him asking for an answer: agreement, sketch, showing or fork; submissions in one sitting count once per goal, while distinct requested reactions count separately. Passive status and ledger reads are attention but not decision cycles; urgent contact counts both an interruption and a cycle. Record the exact candidate and reply for every cycle, including an unchanged rejection; freeze initial par and record authorised revisions, never rewrite the original comparison.

Cause each additional cycle: preventable misunderstanding, failed execution, discovered requirement, necessary authority, external change or his changed intent. Only avoidable causes are waste. Reopening a supposedly finished goal continues its lifetime totals, so early closure cannot improve its score.

The doorway records opened/closed and foreground active time, words displayed/read estimate, words typed, taps, decisions and pushes; idle after 60 seconds is excluded, off-doorway time is marked missing and may be corrected by him. Ledger and recovery minutes count too. Report estimates and missing coverage, not fake precision; a voice request counts speech/transcription time separately.

Per goal: cycles/par, active owner minutes, doer/check/preparation effort, cost, queue age, first-pass rate, later defects and reversals. Per week: sums and medians, all seven scenario attention measures, previous-week comparison, authority/default decisions, new rules and send-backs; ask one optional weekly load rating. Lower cycles with more escaped defects or recovery minutes is failure.

## 9. Trace of the test week

1. **Morning:** gate serves the checked three-item, eight-minute sitting; record accepts Driver ratings agreement, Invoice export candidate and Price page answer, with one cycle on each goal. Nothing else needs him; today's price answer cancels the 5 pm default.
2. **12:40 voice:** capture preserves the reminder symptom and infers project from source/history; counterpart/challenger prepare a one-minute agreement plus receipt-based checks and a proposed lead time. It waits for his next sitting; only bounded diagnosis proceeds before authority, and he holds nothing to remember.
3. **Seventeen forks:** gate logs eleven rule applications and three reversible defaults with deadlines/undo, assuming their accepted agreements delegate those implementation choices; otherwise those three must park too. The three owner-only items enter only within the 12-minute reservation, otherwise their branches park; “three reach him” does not mean three pushes.
4. **Email wrong:** his marks reopen the sketch, record a failed first acceptance and invalidate tone proof; one scope choice rides in the same response. Separate checker challenges the rewritten tone examples before another doer repairs; retry adds a cycle, with misunderstanding versus new taste labelled honestly.
5. **Not now:** record parks Driver ratings on the actual completion event for Faster sign-up, removes its attention reservation and releases work resources. Completion revalidates the agreement and offers the next sketch; a daily watch catches a missing completion signal.
6. **Forty-minute silence:** permission expires within eleven minutes or absent useful progress trips by minute twenty-one; publisher rejects stale output, replacement resumes from a checked artifact, and checker verifies it. Recovery receipt/cost stay in the record; no owner contact if Thursday holds.
7. **Computer off:** observations become unknown within three minutes; watch reroutes movable work, parks hardware-bound work and updates Thursday → Friday when forecast proves the delay. One line, “Shows Friday; the build computer was off,” appears at his next opening, without repeated status pushes.
8. **Sign-in before 3 pm:** an independent check verifies the week-long slip and the lack of delegated sign-in; gate sends one urgent deep link with “Sign in by 3 pm; otherwise release waits a week.” Receipt/retry is mechanical; no answer parks release at 3 pm and records the slip.
9. **Dead question:** daily validation finds its goal moved on; gate withdraws it with source evidence and releases capacity. One ledger line tells him; no answer or new cycle.
10. **Three wording acceptances:** follow-up clocks mature the outcomes; counterpart adds a scoped proposal for delegated completion and random samples, including what still cannot proceed. He sees that proposal once at a sitting; no answer keeps current supervision.
11. **Wrong two days later:** escaped-defect event reopens the accepted goal, suspends that kind's trust/rule and traces related results; bounded rollback/repair runs under existing authority. A checked consequence/repair goes to the next sitting, or the urgent lane if its consequence qualifies; acceptance history stays visible.
12. **Back after three days:** first opening shows current observation age, urgent consequences/moved promises, then at most 12 minutes of live decisions and showings; it offers the ledger after these. Expired items are already withdrawn/defaulted/parked, so he need not read three days of messages; “current in twelve minutes” holds only if he accepts the cap and parking consequences.
13. **Ledger:** scripts derive done goals, actual/par cycles, measured/missing minutes, costs, defaults/rules, questions versus last week and send-back causes; helper explains only consequential exceptions. Missing facts are marked missing; no fabricated weekly totals from an incomplete scenario.
14. **Curiosity:** one-level drill-down reads attempts, computers, current permissions, observation times and full goal cost including recovery; original proof remains accessible. Nothing runs merely because he looked, except an explicitly requested refresh.

Across this trace there is one required doorway and one designed interruption, the sign-in request; backup delivery or a separate incident could add one and is counted. No item requires his private memory because each has a recorded consequence and return. Exact weekly words, taps, decisions and minutes cannot be derived from the supplied events; the eight-minute morning sitting is given, other sittings are bounded at 12 minutes, and the meter measures the rest rather than claiming savings from invented answers.

## 10. What breaks it

| Failure | Catch, bound and recovery |
|---|---|
| Helper stops silently | Ten-minute permission plus one-minute sweep fences publication; progress clock catches a healthy-but-stuck process by minute twenty-one; replacement works in isolation, not on the old writer's live files |
| Wait never resolves | Explicit dependency deadline, daily recheck and next date; authorised alternative or safe park at that deadline; no indefinitely occupied helper |
| Message lost | Durable operation and delivery receipts; reconcile after one minute and retry same number twice; record state, not delivery of a chat message, decides completion |
| False “done” | Maker cannot write acceptance; independent reproduction before showing, counterfeit/missing proof rejected immediately; omitted intent may escape until owner reaction or two-day/random audit and is honestly an unbounded residual risk |
| Restart forgets | A new attempt reads its packet and durable checkpoints; old permissions cannot publish; missing recorded facts produce unknown, not an invented continuation |
| Two change one thing | Reserve dependencies/resources before dispatch; isolated candidates may compete, but only one current permission can publish; atomic version comparison rejects the loser, then integration checks rerun |
| Computer off | Independent host observations stale by three minutes; reroute if movable, otherwise park and recompute promise within five minutes; never infer successful completion from disconnect |
| Record unreachable | Both watch and doorway mark unknown within three minutes; local capture queues only unsent intake and receipts, no new authority or publication; already isolated computation may finish but cannot commit; reconcile operation numbers when service returns |
| Rule wrong | Conflicting instruction, counterexample, failed check or follow-up suspends it immediately; daily expiry scan catches dated staleness, impact query rechecks uses; an undetected semantic mistake has no guaranteed detection time |
| No answers five days | Authorised defaults act; owner-only/irreversible branches park at their stated times; stop new starts when attention reservation fills; day-five view shows current consequences and finite sitting, never five days of reissued questions |

Only the publisher can affect shared/external state; workers without enforceable isolation or restricted credentials may submit patches but cannot run autonomous side effects. Revoking a permission is not proof the old process stopped. Stop/amend/revoke takes effect at the next attempted publication; prior authorised effects need explicit undo, with before/after proof and any loss recorded.

A backed-up single-writer record plus a separate availability observer avoids two competing authorities: restoring or promoting a backup requires fencing the old writer and checking the last committed event. The doorway keeps a dated read-only snapshot; if record, observer and communication all fail together, it cannot promise fresh silence or timely alerts. Restoration and that correlated outage are genuine operational limits, not jobs a replacement helper can solve from memory.

## 11. Cost

A medium six-line goal with two independent work branches takes six judgement runs without rework: agreement, contract challenge, two doers, result checker, showing preparation. About 10–16 event-driven script invocations cover admission, dispatch, checks and completion, plus pooled minute sweeps and one fraction of the weekly ledger; a taste sketch adds a make/check pair and one owner cycle. Rule disputes, repairs and audits are additional recorded runs, not free background work.

Planning budget: counterpart packets around 2,000 words each, doers/checker each one relevant source slice; roughly 15,000–30,000 total words read before tool-heavy work, not a measured prediction. Store actual tokens and money rather than convert these words into a promised bill. Every run has a goal budget; a parallel duplicate needs existing authority and is charged even if discarded.

This spends more on challenging the contract, isolation, reproducible proof and maintaining the record/observer. It spends less on long coordinator histories, healthy wake-ups, handovers and repeated progress summaries; failed checks normally return directly to a doer without an owner cycle. Today's measured example in the method is about fourteen coordinator turns per round with 68% rereading, but a round is not a goal and turns are not equal-cost runs: this is a cost hypothesis, not a numeric saving claim.

## 12. Taking part from anywhere

Minimum participant: receive one packet; fetch permitted inputs; work in isolation; return a candidate or explicit failure with attempt number; report structured cost/checkpoint receipts through a small host wrapper. A helper need not speak to another helper, retain memory, host the record or understand the whole workflow; a computer without connectivity may prepare a candidate but cannot accept fresh authority or publish it.

The wrapper authenticates the computer, advertises capabilities, claims one compatible attempt atomically, renews limited permission, enforces budget/paths and submits a durable result. A board participates by exposing ready work/dependencies and receiving proof-linked outcomes; it is not an independent second authority. A scheduled automation participates as a script doer, checker or watch; it may be incapable of judgement and says so. Assignments to the five named existing systems appear only in the final section.

## 13. The smallest first version

Build one record service with atomic changes and stored proof, one phone/desk doorway with Say/Sit/Glance, a minute watch and separate availability observer, and one host wrapper launchable from two computers. Include agreements, immutable checks, maker/checker separation, timed defaults within explicit authority, stop/revoke/undo, dependency reservations, 12-minute admission and all meter events from the first goal. A manual adapter can submit a file/result initially; do not build a general agent marketplace or a second workflow engine.

Start on reversible wording changes and a bounded report fix; prepare acceptance examples and let existing checks do the mechanical work. Keep full owner showings until he grants narrow delegation; keep trust counts/audit draws but leave automatic broad rule inference, advanced forecasting and automatic record failover out. Each named participant can join through the same packet/receipt contract; richer native adapters can follow measured demand.

Estimate 10–15 engineering days for that bounded version including two-computer fencing, outage/restore rehearsal and meter validation, with uncertainty in permissions and existing interfaces; this is an estimate, not tested capacity. It should beat today by settling already-answered forks and repairing failed checks before showing, not by hiding owner decisions; compare matched kinds against historical goals at once, and count every new real goal from day one. Success requires fewer avoidable cycles and owner minutes without more escaped defects, unobserved stalls or total recovery cost; a retrospective replay cannot establish earned trust or the five-day silence experience.

## 14. Weakest points, method corrections, and existing-tool assignments

1. **The contract can be wrong together with its checker.** Accepted examples and contrary cases reduce this; unfamiliar taste still needs an early reaction. All lines passing cannot certify latent intent, and check counts can mislead if presented as completeness.
2. **Independence costs more than another session.** Evidence separation, reproducible tests and different review methods help, but correlated errors and weak judgements remain; provider diversity is neither always available nor a proof.
3. **Quiet depends on real enforcement and independent observation.** A host wrapper without publication/credential control cannot safely fence an old doer; correlated record/watch outages break alert guarantees. Some outside actions cannot be undone at all and therefore remain owner-gated.

The method should minimise attention subject to correctness, recovery and effort limits; attention is not the only scarce resource. A minute is a target, not a guarantee; agreement may reopen on discovery, extra cycles are not all waste, answers are scoped rulings rather than eternal preferences, and cap size must follow minutes/age rather than seven items. Trust can omit a showing under explicit authority; it cannot turn subjective success into a machine fact or safely remove oversight of irreversible acts.

Evidence used: the method's measurements and `../research/d5-outside.md`, especially sections 1, 2 and 4. The research supports these cautions, not the proposed clock settings, autonomy thresholds or build estimate; those need calibration in use.

Existing tools, considered only after the design: these are possible assignments, not a claim that the assembled machine exists. Read-only help inspected here: `orca skills get orchestration`, `orca skills get orca-cli`, `claude --help`, `codex exec --help`, `bd --help`, `wmill --help`, `wmill schedule --help`, `wmill job --help`; no real dispatch, board change, job or end-to-end interoperability was tested.

| Existing participant | Need it could fill | Still needed around it |
|---|---|---|
| Orca-run helpers | Start an agent in an isolated workspace; carry task/dispatch identity and result receipts; expose placement and work detail | Contract/check schema, common record and gate; verify that actual permissions and publication fencing hold across hosts, rather than treating silence or a terminal exit as proof |
| Claude Code command-line helpers | A fresh print-mode process takes a bounded packet and returns structured output; tool restrictions/budget options support a constrained doer or checker | Host wrapper, durable attempt identity, isolated artifacts and independent proof; permission configuration must honour existing authority |
| Codex command-line helpers | A fresh noninteractive execution takes a packet and emits structured events plus a final response conforming to a schema | Same wrapper/record, resource and publication control, proof capture and independent checker; structured output alone says nothing about truth |
| Beads board | Ready tasks, dependencies, claim/heartbeat/reclaim, provenance and proof-linked completion; useful as a linked work queue | Map each task to one agreement/attempt; reconcile duplicate events; keep board status distinct from checked/accepted goal state; never use reclaim alone to prove the old writer stopped |
| Windmill | Run script/flow work and scheduled watches; inspect job/result receipts and reroute script work | Implement record-facing jobs, gate and observer; an observer on a different failure domain; scheduled execution is not judgement or automatic authority |

None by itself supplies the complete checked agreement, calibrated taste boundary, cross-system authority, trustworthy observation and common attention/cost meter. A transactional database and fingerprinted file store could hold the record; a small service must enforce its transitions, and a single responsive doorway must show the five moments. This file chooses those responsibilities, not an untested product replacement; it adds no code, configuration, schedule, board entry or page.
